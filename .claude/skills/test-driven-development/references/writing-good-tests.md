# 良いテストの書き方

**読むタイミング:** テストを書く／変更する、モックを足す、テスト用ヘルパーを足すとき。

## 2つの原則

```
1. すべてのテストは「どの壊れ方を捕まえるか」を名指しできる
2. すべてのテストは「本物」を動かす
```

厳密な TDD はこの2つを自然に満たす。先に書いて実コードに対して落ちるのを見たテストは、
すでに「落ちうること」を証明している。モックは、実物が遅い／外部依存だと分かってから初めて使う。

## 原則1: どの壊れ方を捕まえるか名指しする

テスト本体を書く前に答える。
**「本番コードがどう変わったらこのテストは落ちるか。その変更はバグか、それとも意図的な決定か。」**

捕まえる価値があるのは、分岐の誤り・副作用の欠落・引数の誤り・境界条件・契約違反である。

### 期待値は自力で導出する

リテラルや手計算した固定値を使う。テーブル駆動テストで `want` をリテラルで並べる形が最も良い。
**テスト対象（やそのヘルパー）で期待値を計算すると、コードが何をしても通る。**

```ts
// ❌ 鏡写しアサーション: 両辺を同じ実装が計算している。常に通る
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手で導出したリテラル
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

### 変更検知テストを書かない

意図的な決定（定数の値、メッセージの文言、内部構造）でしか落ちないテストは、
**設計変更のたびに落ち、バグは素通りさせる。**

決定に依存する「振る舞い」を検証する。
`expect(MAX_RETRIES).toBe(5)` ではなく、
「失敗する呼び出しが5回リトライされ、6回目は実行されない」を検証する。

### テキストではなく振る舞いを検証する

スクリプトや設定ファイルに特定の行が含まれることをアサートしても、
「ソースがソースであること」しか証明できない。
スクリプトは制御された入力で実行し、出力・副作用・終了コードを検証する。
人間向けの文章はテスト対象ではない。

### フレームワークではなく自分のコードを検証する

自分のコードが境界で結んでいる契約（登録したルート、発行するクエリ、生成するペイロード）を検証する。
上流の仕様は上流の担当である（典型例: 「登録したハンドラがルータから呼ばれること」の検証は
フレームワークのテストであって、あなたのテストではない）。

上流の挙動に本当に驚かされた場合のみ、前提を名指しした特性テストを1本だけ書く。

同じ境界線は自分のコードの内側にも適用される。コンストラクタ・getter・定数・単純な委譲は、
検証・正規化・デフォルト適用・導出・強制・副作用のいずれかを行うときだけテストする価値がある。
そうでなければ、それらに依存する「最初に外から見える結果」を検証する。

### ゲート関数

```
テスト本体を書く前に:
  本番コードのどの変更でこのテストが落ちるかを名指しする

  名指しできない          → 観測可能な振る舞いを軸に設計し直す
  「ソースの文字列が変わる」 → 成果物を実行して効果を検証する
  意図的な決定でしか落ちない → 変更検知テスト。決定に依存する振る舞いを検証する

  期待値がテスト対象のロジック／ヘルパーを使っていないか確認する
  使っている → リテラルか手計算した固定値に置き換える
```

## 原則2: 本物を動かす

### モックにアサートしない

モックへのアサーションは、モックがあれば通り、無ければ落ちる。
**対象コンポーネントについて何も語っていない。**

```ts
// ✅ 実際の振る舞い
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ モックの存在確認
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

判定: 「これはモックの振る舞いを検証していないか？」

### 正しい層でモックする

実物のメソッドの副作用をすべて把握してから置き換える。
**遅い／外部依存の操作だけをモックし、テストが依存している部分は実物のまま残す。**

```ts
// ❌ モックが、重複検出が読む設定書き込みごと飲み込んでいる
vi.mock('ToolCatalog', () => ({ discoverAndCacheTools: vi.fn().mockResolvedValue(undefined) }));

// ✅ 遅いサーバ起動だけをモックし、設定書き込みは実物のまま
vi.mock('MCPServerManager');
```

迷ったら、まず実物に対してテストを走らせ、実際に何が起きる必要があるのか観測する。

### テストダブルは具体的に作る

引数・呼び出し回数・順序が契約の一部なら、それらをアサートする。何でも受け取るフェイクは何も検証しない。
分岐（成功・エラー・不正データ）ごとにフィクスチャやスパイを分け、
**間違った分岐が期待を満たせないようにする。**

### モックのデータ構造は実物と同形にする

テストが読むフィールドだけでなく、実在する構造を漏れなく再現する。
部分的なモックは、下流が省いたフィールドを読んだときに黙って壊れる
（テストは通るのに結合すると壊れる）。

### 本番クラスには本番メソッドだけ置く

テストだけが必要とする後片付けは、テストユーティリティに置く。本番クラスの `destroy()` にしない。
判定: このメソッドはテストからしか呼ばれないか／このクラスはこのリソースのライフサイクルを所有しているか。

### モックが膨らんだら実物に切り替える

モックのセットアップがテスト本体より長い、実物にあるメソッドがモックに無い、
モックを変えるとテストが壊れる——いずれも結合テストに切り替えるサイン。
判定: 「ここでモックを使う必要は本当にあるか？」

### ゲート関数

```
モックやテストヘルパーを足す前に:
  実物のメソッドの副作用を列挙する
  → テストが依存しているものは実物のまま残す
  → その下の遅い／外部の層だけをモックする

  モックの戻り値は実物の構造を完全に再現する
  テストからしか呼ばれないメソッドはテストユーティリティへ
  モック自体にアサートしそうになったら、モックを外すかアサートを消す
```

## テストは実装と一緒に出す

失敗するテスト → 最小実装 → リファクタ、これが「完了」の定義である。
**必要なテストだけを出す。** 自明なコードや人間向けの文章にテストは要らない。
プロセスを満たすためだけのテストは、永続的な保守コストになる。

## ミューテーションチェック（仕上げ）

本番コードを頭の中で変異させ、**現実的な変異それぞれに対して最低1つのテストが落ちる**ことを確認する。

- 定数や引数を間違える
- 分岐のハンドラを取り違える
- 状態変更・副作用を消す
- 空やデフォルト値を返すようにする
- ゼロ／空／null／未認可／不正入力の検証を消す

どのテストも落ちない変異があれば、その振る舞いは無防備か、テストがトートロジーである。

## クイックリファレンス

| 場面 | やること |
|---|---|
| テストを書く | 捕まえる壊れ方を名指しする（決定ではなくバグ） |
| 期待値を作る | 手で導出する。テスト対象で計算しない |
| スクリプトや文書を検証する | 実行して効果を見る。文字列 grep はしない |
| 依存ライブラリを検証したくなる | 自分の境界の契約を検証する |
| モック要素にアサートしたくなる | 実物を検証するか、モックを外す |
| モックしようとしている | 副作用を把握し、遅い／外部の層をモックする |
| モックの戻り値を作る | 実物の構造を完全に再現する |
| テスト専用の後片付けが要る | テストユーティリティに置く |
| モックのセットアップが膨らむ | 実物を使う結合テストに切り替える |
| テストファイルを仕上げる | ミューテーションチェックを回す |

## 警告サイン

- セットアップとアサーションが同じオブジェクトを共有していて、等価が保証されている
- 例外・クラッシュ・セレクタ欠落でしか落ちない
- 意図的な変更のたびに落ち、事故では落ちない
- 期待値がループ・ビルダー・ヘルパーの奥に隠れている
- ソースの文字列を grep している
- フレームワークだけ残しても意味が通る
- カバレッジのためだけにあり、副作用も結果も見ていない
- `*-mock` の testId をアサートしている／モックを外すと落ちる
- テストファイルからしか呼ばれないメソッドがある
- モックのセットアップがテストの半分以上を占める／なぜ必要か説明できない
- 「念のため」モックしている
