# test-driven-development — 先にテスト、次に実装

**原則: 失敗を目で見ていないテストは、正しいものを検証しているか分からない。**

**字面を破ることは趣旨を破ることである。**

## 鉄則

```
失敗するテストなしに、本番コードを書かない。
```

テストより先にコードを書いてしまったら、**消してやり直す**。

- 「参考に残す」→ しない
- 「見ながら書き直す」→ それはテスト後追いである
- 消すとは消すこと

## 適用範囲

**常に適用:** 新機能 / バグ修正 / リファクタ / 振る舞いの変更

**例外（人間に確認してから）:** 使い捨てのプロトタイプ / 生成コード / 設定ファイル /
純粋な文章・ドキュメント / 見た目だけの CSS 調整

「今回だけ TDD を飛ばそう」と思ったら、それは合理化である。止まる。

## テストランナーが無いリポジトリでの適用

本リポジトリ群には、ビルド不要の静的 HTML/JS アプリ（`game-apps`, `daily-useful-tools` 等）が含まれる。
**「テストランナーが無い」は TDD を飛ばす理由にならない。** 次の順で降りていく。

1. **ロジックを純関数に切り出せるか** → 切り出して `node --test` で普通に TDD する（推奨）
2. **切り出せない DOM 依存部分** → ブラウザで実行する最小の検証ページ／スクリプトを先に書き、
   **失敗する（= 期待どおり動かない）ことを先に確認してから**実装する
3. **1 も 2 も不可能な場合のみ** → 実装前に「受け入れ条件（観測可能な形で）」を文章で書き出し、
   実装後にその1件ずつを実機で照合する。**この場合は「TDD を適用していない」と明示的に報告する**

3 を選ぶときは、その理由を報告に必ず書く。黙って 3 に落ちるのは禁止。

## RED-GREEN-REFACTOR

```
RED       失敗するテストを書く
  ↓
検証      実行して、期待どおりの理由で失敗することを確認（省略不可）
  ↓
GREEN     通すための最小限のコードを書く
  ↓
検証      実行して通ること・他が壊れていないことを確認（省略不可）
  ↓
REFACTOR  重複除去・命名改善（振る舞いは変えない、緑のまま）
  ↓
コミット → 次の RED へ
```

### RED — 失敗するテストを書く

1つの振る舞いだけを、意図が読める名前で書く。

```ts
// ✅ 名前が振る舞いを説明し、実コードを動かし、1つのことだけ見ている
test('失敗した処理を3回までリトライする', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

```ts
// ❌ 名前が曖昧で、検証しているのはモックの挙動
test('リトライが動く', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```

要件: 振る舞いは1つ / 名前で分かる / 実コードを動かす（モックは避けられないときだけ）

### 検証 RED — 失敗を見る（省略不可）

```bash
npm test -- tests/foo.test.ts
```

確認すること:
- **失敗**している（エラーで落ちているのではない）
- 失敗メッセージが想定どおり
- 「機能が無いから」失敗している（誤字やimport漏れではない）

**通ってしまった** → 既存の振る舞いを検証している。テストを見直す。
**エラーで落ちた** → エラーを直し、正しく失敗するまで繰り返す。

### GREEN — 最小限のコードを書く

```ts
// ✅ 通すのに必要なだけ
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try { return await fn(); } catch (e) { if (i === 2) throw e; }
  }
  throw new Error('unreachable');
}
```

```ts
// ❌ テストが要求していないオプションを生やしている（YAGNI 違反）
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: { maxRetries?: number; backoff?: 'linear' | 'exponential' },
): Promise<T> { /* ... */ }
```

機能追加・周辺のリファクタ・「ついでの改善」をここでやらない。

### 検証 GREEN — 通ることを見る（省略不可）

- 対象テストが通る
- **他のテストも通る**
- 出力がきれい（想定外の警告・エラーが出ていない）

テストが落ちる → **コードを直す。テストを緩めない。**

### REFACTOR — 片付ける

緑になってからのみ。重複除去・命名改善・ヘルパー抽出。
**振る舞いは変えない。緑を保つ。**

## 良いテストの条件

| 観点 | 良い | 悪い |
|---|---|---|
| 最小 | 1つのことだけ。名前に「かつ」が入るなら分割 | `test('メール検証とドメイン検証と空白除去')` |
| 明確 | 名前が振る舞いを説明する | `test('test1')` |
| 意図 | 望ましい API の姿を示す | 何をすべきか読み取れない |

テストを書く・変える・モックを足すときは `references/writing-good-tests.md` を読む。要点:

- 書く前に「本番コードのどの変更でこのテストが落ちるか」を言語化する
- 期待値は手で導出する（テスト対象のコードで計算しない）
- モックの挙動をアサートしない。実物の振る舞いをアサートする
- テストだけが使うメソッドは本番クラスに置かない
- モックする前に、実物の副作用を把握する

## 言い訳と現実

| 言い訳 | 現実 |
|---|---|
| 「単純すぎてテスト不要」 | 単純なコードも壊れる。テストは30秒で書ける |
| 「あとでテストを書く」 | 後から書いたテストは最初から通る＝何も証明していない。落ちるところを見ていない |
| 「後追いでも目的は同じ（形式より精神）」 | 後追いは「これは何をするか」に答える。先行は「何をすべきか」に答える。既に書いたコードに引きずられる |
| 「手で動作確認した」 | 記録が残らず、変更のたびに再実行できず、条件の抜けに気づけない |
| 「何時間もかけたコードを消すのは無駄」 | サンクコスト。その時間はどちらにせよ戻らない。信頼できないコードを残すほうが損 |
| 「参考に残して、テストを先に書く」 | 結局それを見て書く＝後追い。消す |
| 「まず探索が必要」 | よい。探索コードは捨てて、TDD で書き直す |
| 「テストしづらい」 | 設計が不明瞭というシグナル。テストの声を聞く |
| 「TDD は遅い」 | コミット前にバグが出る／安心してリファクタできる。本番で直すほうが遅い |
| 「既存コードにテストが無い」 | あなたが触る範囲から足す |

## 停止シグナル（該当したら消してやり直す）

- テストより先にコードを書いた
- 実装のあとにテストを書いた
- テストが最初から通った
- なぜ落ちたか説明できない
- 「今回だけ」と考えている
- 「もう手で確認した」
- 「参考に残す」「これをベースに直す」
- 「もう何時間もかけたから」

## 完了前チェックリスト

- [ ] 新しい関数・メソッドにテストがある
- [ ] 各テストが落ちるところを自分で見た
- [ ] 落ちた理由が「機能が無いから」だった（誤字ではない）
- [ ] 通すための最小限のコードを書いた
- [ ] 全テストが通る
- [ ] 出力がきれい（想定外の警告なし）
- [ ] テストは実コードを動かしている（モックは不可避な箇所のみ）
- [ ] 境界値・異常系を含んでいる

全部にチェックが付かない → TDD を飛ばしている。やり直す。

## 詰まったとき

| 症状 | 対処 |
|---|---|
| テストの書き方が分からない | 望ましい API を先に書く。アサーションから書く。人間に聞く |
| テストが複雑すぎる | 設計が複雑すぎる。インターフェースを単純化する |
| 全部モックしないと動かない | 結合が強すぎる。依存性注入にする |
| セットアップが巨大 | ヘルパーに抽出。それでも複雑なら設計を見直す |

## デバッグとの接続

バグを見つけたら、**まず再現する失敗テストを書く**。そのうえで TDD サイクルを回す。
テストが修正の証明になり、同時にリグレッションを防ぐ。
原因特定の手順は `systematic-debugging` スキルに従う。

**テストなしでバグを直さない。**
