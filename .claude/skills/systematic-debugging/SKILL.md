# systematic-debugging — 原因を特定してから直す

**原則: 修正の前に必ず根本原因を突き止める。対症療法は失敗である。**

**手順の字面を破ることは、デバッグの趣旨を破ることである。**

## 鉄則

```
フェーズ1（根本原因調査）を終えるまで、修正案を出してはならない。
```

## 使う場面

あらゆる技術的問題に使う。テスト失敗 / 本番バグ / 想定外の挙動 / 性能劣化 / ビルド失敗 / 連携不具合。

**特に使うべきとき:**
- 急いでいるとき（焦りは当て推量を誘発する）
- 「たぶんこれが原因」と一目で分かった気がするとき
- すでに複数回修正を試したとき
- 前の修正が効かなかったとき
- 自分が現象を完全には理解していないとき

**飛ばしてよい例外はない:**
- 「単純そうだから」→ 単純なバグにも原因がある。手順は単純なバグほど速く終わる
- 「時間がないから」→ 当て推量の往復のほうが遅い

## 4フェーズ

各フェーズを完了してから次に進む。

### フェーズ1: 根本原因の調査

**いかなる修正にも着手する前に。**

1. **エラーメッセージを最後まで読む**
   - 警告も飛ばさない。スタックトレースは全行読む
   - 行番号・ファイルパス・エラーコードを控える
   - エラーメッセージが答えそのものであることは珍しくない

2. **確実に再現する**
   - 再現手順を確定させる。毎回起きるか、条件付きか
   - 再現できない → データを増やす。**推測で直さない**

3. **直近の変更を確認する**
   - `git diff` / `git log` / 依存の更新 / 設定変更 / 環境差分
   - 「直前まで動いていた」なら差分の中に原因がある

4. **多層システムでは証拠を集める**

   複数のコンポーネントをまたぐとき（CI → ビルド → デプロイ、UI → API → DB など）、
   **修正案を出す前に、境界ごとに観測を入れる。**

   ```
   各コンポーネント境界について:
     - 入ってくるデータを記録する
     - 出ていくデータを記録する
     - 環境変数・設定が伝播しているか確認する
     - 各層での状態を確認する

   1回動かして「どこで壊れているか」を示す証拠を得る
   → 壊れている層を特定する
   → その層だけを調査する
   ```

   これで「秘密情報はワークフローには届いている（✓）／ビルドスクリプトには渡っていない（✗）」
   のように、**壊れている境界が一意に定まる**。

5. **データフローを遡る**

   エラーがコールスタックの深い位置で出ているとき → `references/root-cause-tracing.md`

   要点: 不正な値はどこで生まれたか → 誰がその値を渡したか → 源流まで遡る → **源流で直す**。

### フェーズ2: パターン分析

1. **動いている例を探す** — 同じリポジトリ内の類似コードで、動いているものはどれか
2. **参照実装を最後まで読む** — 流し読みは禁止。パターンを適用する前に全部読む
3. **差分を列挙する** — 動くものと壊れているものの違いを、些細に見えるものも含めて全部挙げる
4. **依存関係を把握する** — 必要な設定・環境・前提は何か

### フェーズ3: 仮説と検証

1. **仮説を1つだけ立てる** — 「Y だから X が根本原因だと考える」と明文化する
2. **最小の変更で検証する** — 一度に1変数。複数同時に直さない
3. **確認してから進む** — 効いた → フェーズ4 / 効かない → **新しい仮説を立てる**（修正を重ねない）
4. **分からないときは分からないと言う** — 分かったふりをしない

### フェーズ4: 実装

1. **失敗するテストを先に作る**
   - 最小の再現。自動テストが理想、無理なら再現スクリプト
   - **修正前に必ず用意する**
   - 書き方は `test-driven-development` スキルに従う

2. **1つだけ直す**
   - 特定した根本原因に対して。1変更ずつ
   - 「ついでに」のリファクタや改善を混ぜない

3. **検証する**
   - テストが通るか / 他が壊れていないか / 現象が実際に消えたか
   - 完了を報告する前に `verification-before-completion` スキルを通す

4. **直らなかったら**
   - 止まる。**何回目の修正か数える**
   - 3回未満 → フェーズ1へ戻り、得た情報込みで再分析
   - **3回以上 → 修正をやめて設計を疑う（次項）**

5. **3回失敗したら設計を疑う**

   設計の問題を示すサイン:
   - 修正のたびに別の場所で新しい共有状態・結合・問題が見つかる
   - 修正に「大規模なリファクタ」が必要になる
   - 修正するたびに別の症状が出る

   **前提に立ち返る:** この構造はそもそも妥当か / 惰性で維持しているだけではないか /
   症状を潰し続けるより設計を変えるべきではないか

   → **4回目の修正に進む前に、人間に相談する。** これは仮説の失敗ではなく設計の誤りである。

## 停止シグナル（こう考えたら手順に戻る）

- 「とりあえず直して、後で調べる」
- 「X を変えてみて様子を見る」
- 「まとめて何か所か変えてテストを回す」
- 「テストは省いて手で確認する」
- 「たぶん X だから直す」
- 「よく分からないがこれで動くかもしれない」
- 「参照実装は長いので適当に合わせる」
- データフローを追う前に解決策を並べ始めている
- **「あと1回だけ試す」（すでに2回以上失敗している）**
- **修正のたびに別の場所で問題が出ている**

**いずれもフェーズ1に戻れという意味である。**

## 人間からの「やり方が違う」シグナル

- 「それ本当に起きてる？」→ 検証せずに前提を置いている
- 「それで原因わかるの？」→ 証拠を集める工程を飛ばしている
- 「当てずっぽうはやめて」→ 理解せずに修正案を出している
- 「根本から考えて」→ 症状ではなく前提を疑えという意味
- 「詰まってる？」→ 今のアプローチが機能していない

**いずれも即座にフェーズ1へ戻る。**

## 言い訳と現実

| 言い訳 | 現実 |
|---|---|
| 「単純だから手順は不要」 | 単純なバグにも原因がある。手順は数分で終わる |
| 「緊急だから時間がない」 | 当て推量の往復のほうが遅い |
| 「まず試してから調べる」 | 最初の修正が以後の方針を決める。最初から正しくやる |
| 「効くか確認してからテストを書く」 | テストのない修正は定着しない |
| 「まとめて直せば速い」 | 何が効いたか分からず、新しいバグを生む |
| 「参照実装は長いので要約で足りる」 | 部分的理解はバグを保証する |
| 「原因が見えた、直そう」 | 症状が見えたことと原因の理解は別物 |
| 「あと1回」（2回以上失敗後） | 3回失敗＝設計の問題。修正を重ねない |
| 「フレーキーなだけ」 | フレーキーは原因名ではない。再現条件を特定する |

## クイックリファレンス

| フェーズ | やること | 完了条件 |
|---|---|---|
| 1. 根本原因 | エラー精読・再現・差分確認・境界での証拠収集 | 何がどこでなぜ起きているか言える |
| 2. パターン | 動く例を探す・参照実装を読む・差分を列挙 | 違いが特定できている |
| 3. 仮説 | 仮説を1つ立て、最小変更で検証 | 確定 or 新しい仮説 |
| 4. 実装 | 失敗するテスト → 1つ修正 → 検証 | 現象が消え、テストが通る |

## 「根本原因がない」と結論する前に

調査の結果、環境依存・タイミング依存・外部要因だと判明した場合:

1. 調査した内容を記録する
2. 適切なハンドリング（リトライ・タイムアウト・エラーメッセージ）を実装する
3. 将来の調査のためにログ／監視を足す

**ただし「原因不明」の大半は調査不足である。** タイミング依存のテストは
`references/condition-based-waiting.md` を読む（多くは固定 sleep が原因で、これは直せる）。
