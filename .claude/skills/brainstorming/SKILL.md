# brainstorming — アイデアを設計に変える

対話でアイデアを設計・仕様に落とす。**分類 → 文脈把握 → 具体化 → 設計提示 → 承認**の順に進む。

<HARD-GATE>
何を作るつもりかを人間に伝え、承認を得るまでは、
実装スキルの起動・コードの記述・プロジェクトの雛形生成・その他の実装行為を行わない。
これは下記すべての経路のすべてのタスクに適用される。
**儀式の重さはタスクに応じて変わるが、承認ゲートは変わらない。**
</HARD-GATE>

## 3つの経路

最初の質問をする前に分類し、**分類を声に出す**（人間が覆せるように）。
例:「これは範囲が限定的なので、仕様書は書かずにこの場で短い設計を出します」

### Spike（調査）
「できる？」「可能？」「雑でいいから」という**実現可能性の問い**。成果物は答えであって、残すコードではない。

- 問いと試すことを2〜3文で提示 → 了承 → 正しさを損なわない範囲で最速で確かめる
- 設計文書も仕様ファイルも作らない
- 結果は推奨として報告し、作ったものは「使い捨て」と明記する

### Bounded（限定的）
**このリポジトリに既にあるコード**への、範囲の限定された変更。フラグ追加、小さなエンドポイント、1ファイルの修正。

- 「どういう種類のアプリか分かる」では足りない。**変更対象のフローが既に読める状態にあること**が条件
- 変更すべき既存フローが無いなら、それは Bounded ではない
- 重要な確認質問をする → **チャット上で**短い設計（数文〜数段落）を提示 → **止まる**
- 人間が「はい」と言ってから実装に入る。仕様ファイルも実装計画書も作らない

### Architectural（構造的）
新規プロジェクト、新しいサブシステム、コンポーネント間の構成を変える変更、他が依存するインターフェースの変更。

- 全工程を通す（質問 → 選択肢 → 節ごとの設計提示 → 仕様書 → `writing-plans`）

**どちらか迷ったら重いほうを選ぶ。** ラチェットは一方向: 途中で複雑さが露見したら経路を上げる
（止まって、そう宣言する）。途中で下げることはない。

## アンチパターン:「単純すぎて承認は要らない」

どの経路も、実装前に人間が意図を承認して終わる。
TODO リスト1つ、ユーティリティ関数1つ、設定変更1つでも、
**設計はチャット2文でよいが、提示して承認を得ること自体は省略できない。**
「単純な」タスクこそ、検証されていない前提が最も無駄を生む。
単純さに応じて縮むのは成果物であって、承認ではない。

## 停止シグナル

| 思考 | 現実 |
|---|---|
| 「単純すぎて設計は不要」 | 単純＝設計が短い、であって設計が無い、ではない。2文出して承認をもらう |
| 「Bounded 扱いにして仕様書を省こう」 | 省くためにラベルを探している時点で迷いがある。重いほうを取る |
| 「設計は明らかなので、読んでもらう間に着手する」 | ゲートは設計の長さではなく承認。提示して、はいを聞くまで止まる |
| 「この種のアプリは分かっているから Bounded」 | Bounded が測るのはリポジトリであって、あなたの慣れではない。新規プロジェクトは Architectural |
| 「Spike がうまくいったのでコードを残す」 | Spike の成果は答え。残すのは新しい依頼。分類し直す |
| 「膨らんだがもう終わりそうなので分類し直さない」 | 隠れた複雑さは経路を上げる。止まって宣言する |
| 「Spike を承認されたので続きの変更も承認済み」 | タスクごとに分類と承認を取る |

## 各経路のチェックリスト

分類し、経路を宣言し、項目ごとにタスクを作って順に進める。

**Spike:**
1. プロジェクトの文脈を把握する（問いを組み立てるのに必要な分だけ）
2. 問いと調べ方を2〜3文で提示する
3. 承認を得る（うなずき程度でよい）
4. 調べる（正しさを損なわない範囲で最安の方法で）
5. 推奨として報告する。作ったものは使い捨てと明記する

**Bounded:**
1. プロジェクトの文脈を把握する（該当ファイル・ドキュメント・直近のコミット）
2. 確認質問をする（1度に1つ、意味のあるものだけ）
3. チャットで短い設計を提示する（方針 / 触るファイル / 検証方法）
4. **承認を待つ。** 提示と着手を同じ発言でやるのはゲート破り
5. 実装する（通常の開発フロー。TDD を適用）。計画書は作らない

**Architectural:**
1. プロジェクトの文脈を把握する（ファイル・ドキュメント・直近のコミット）
2. 確認質問をする（1度に1つ。目的・制約・成功条件を理解する）
3. **市場・先行事例・技術選択肢を調べる**（下記「調査」参照）
4. 選択肢を2〜3案、トレードオフと推奨付きで提示する
5. 設計を**節に分けて**提示し、節ごとに承認を得る（複雑さに応じた粒度で）
6. 設計文書を書く → `docs/specs/YYYY-MM-DD-<topic>-design.md` に保存してコミット
7. セルフレビュー（下記）
8. 人間に保存した仕様を読んでもらう
9. `writing-plans` スキルに移行して実装計画を作る

## 質問の仕方

- **1度に1つ。** まとめて投げると、どれも浅い答えしか返らない
- 前に進む判断が変わる質問だけをする。常識的な既定値で決まることは自分で決めて、決めたと伝える
- 「どうしますか？」ではなく「A と B があり、◯◯の理由で A を推します。よいですか？」

**必ず聞くべきこと:**
- 誰が使うのか / 何ができたら成功なのか
- 明示的な非ゴール（作らないもの）
- 制約: 期限・対応ブラウザ／端末・オフライン可否・データの保存先・費用
- 既存資産のどれを再利用するか

## 調査（Architectural のみ）

設計を提示する前に、次を確認して出典を添える。

- 同種のツール／アプリの既存事例と、そこで標準になっている UX
- 使用を検討しているライブラリ・API の**現在のステータスと最新バージョン**
  （記憶に頼らず一次情報を確認する。Preview / GA / 非推奨 / 廃止予定は特に）
- 取得日・URL・公式／非公式の別を併記する
- 未検証・推測の部分は推測であると明示する。断定と推測を混ぜない

## 設計文書の構成

```markdown
# <機能名> 設計

**日付:** YYYY-MM-DD
**ステータス:** ドラフト / 承認済み

## 解決する問題
（誰の、どの困りごとか。1〜3文）

## ゴール / 非ゴール
- ゴール:
- 非ゴール:（作らないものを明示する）

## 受け入れ条件
- [ ] 観測可能な形で書く（「使いやすい」ではなく「初回操作まで3クリック以内」）

## 検討した選択肢
| 案 | 利点 | 欠点 | 採否 |

## 採用する設計
（構成・データの流れ・主要なインターフェース）

## 技術選定と理由
（バージョン・ステータス・出典を添える）

## 制約とリスク
（性能・互換性・コスト・セキュリティ・不確実な前提）

## 検証方法
（受け入れ条件をどう確かめるか）
```

## セルフレビュー（仕様を保存したあと）

自分で回すチェック。サブエージェントには投げない。

1. **プレースホルダ**: 「TBD」「後で詰める」「適切に処理する」が残っていないか
2. **矛盾**: 前の節と後ろの節で違うことを言っていないか
3. **曖昧さ**: 受け入れ条件は観測可能な形か
4. **スコープ**: 非ゴールに書いたものが設計に紛れ込んでいないか

見つけたらその場で直す。

## 破壊的・不可逆な操作について

設計段階で、次に該当する操作が含まれると分かったら、**設計提示時に明示して個別の承認を取る。**

- データやファイルが消える可能性のあるもの（削除・初期化・上書き）
- 本番環境・課金・外部公開・不可逆な変更
- 認証情報・権限・セキュリティに関わるもの

## 実装への移行

- **Spike** → 調査して報告。コードは残さない
- **Bounded** → 承認後、`test-driven-development` に従って実装
- **Architectural** → `writing-plans` スキルで実装計画を作る
