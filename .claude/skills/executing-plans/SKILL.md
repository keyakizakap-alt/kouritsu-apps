# executing-plans — 計画を実行する

計画を読み込み、批判的にレビューし、全タスクを実行し、完了を報告する。

**開始時に宣言する:**「executing-plans スキルでこの計画を実装します」

## ステップ1: 読み込みとレビュー

1. 作業ブランチにいることを確認する（本リポジトリ群の運用については CLAUDE.md を参照。
   **`main` / `master` 上で実装を始めない**）
2. 計画ファイルを読む。計画が参照している設計文書も読む
3. **批判的にレビューする** — 疑問・懸念・矛盾・抜けを洗い出す
4. 懸念があれば、**着手前に**人間に伝える
5. 懸念が無ければ、タスクごとに TODO を作って進む

## ステップ2: タスクの実行

各タスクについて:

1. 進行中にする
2. ステップを**そのとおりに**実行する（計画のステップは2〜5分粒度になっている）
3. 計画が指定する検証を実行する。**出力を読む**
4. コミットする
5. 完了にする

**タスクごとに守ること:**
- 実装は `test-driven-development` スキルに従う（テストを先に書き、失敗を見る）
- 失敗に遭遇したら `systematic-debugging` スキルに従う（当て推量で直さない）
- タスクを完了とする前に `verification-before-completion` スキルを通す
- 計画に無い改善を「ついでに」入れない。必要だと思ったら記録して、人間に出す

## ステップ3: 完了

全タスクが完了し検証できたら:

1. **リポジトリの全体検証を実行する**（CLAUDE.md の検証コマンド）
2. 計画の受け入れ条件を1件ずつ照合し、**未達があれば明示する**
3. 作業ブランチにプッシュし、ドラフト PR を作成する
4. 完了報告には**実行したコマンドと出力**を添える（`verification-before-completion`）

## 止まって聞くべきとき

**ただちに実行を止める:**
- ブロッカーに当たった（依存が無い、テストが通らない、指示が不明瞭）
- 計画に致命的な抜けがあり着手できない
- 指示の意味が分からない
- 検証が繰り返し失敗する
- 計画の前提が現実と食い違っている（API が変わっている、ファイルが存在しない等）

**推測で進めず、確認する。** ブロッカーを力技で越えない。

## ステップ1に戻るとき

- 人間がフィードバックを受けて計画を更新した
- 方針そのものを考え直す必要が出た

## レビュー指摘を受けたら

CI・bot・人間・サブエージェントから指摘が来たら、**コードを編集する前に `review-triage` スキルを通す。**
指摘を1件ずつ潰していくと、修正と再指摘のループに入る。

## 要点

- 先に計画を批判的にレビューする
- ステップはそのとおりに実行する
- 検証を飛ばさない
- 計画がスキルを指定していたらそれを使う
- 詰まったら止まる。推測しない
- `main` / `master` で実装を始めない
