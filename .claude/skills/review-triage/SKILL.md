# review-triage — レビュー沼を抜けるためのトリアージ・ゲート

観点別に並列で走らせたレビュワーの指摘に素直に従うと、こうなる。

- レビュワーの提案は**症状への処方**であることが多く、根本原因が残って別の形で再発する
- 観点Aを満たす修正が観点Bの不合格条件を踏み、**指摘が無限に生成される**
- 目的が「Issue の解決」から「**レビュワー全員の合格**」にすり替わる

**修正コードを書く前に必ず通す関所である。**

## 原則（迷ったらここに戻る）

1. **Done は「Issue の解決＋リグレッションなし」。「レビュワー全員の合格」ではない。**
2. **指摘された「問題」は信じる。指摘された「修正方法」は仮説として扱う。**
3. **却下は正当な結論である。** 根拠を書いて返すのは仕事であり、サボりではない。
4. **同じテーマの指摘が2回目に出たら、前回の修正が浅かったサイン。** 3回目はループ確定。
5. **修正は「指摘ごと」ではなく「根本原因ごと」に、1つの統合パッチとして設計する。**

## 手順

### 1. ゴールを書き出す（省略不可）

コードに触れる前に。ラウンドごとに読み直す。

```
- 解決しようとしている問題:
- 受け入れ条件: [ ] 条件1  [ ] 条件2
- 非ゴール:
```

受け入れ条件に紐づかない指摘は、スコープ外候補（分類 B）である。

### 2. 全指摘を1枚の表に集約して分類する

観点別レビュワーが別々に返してきた指摘も、**必ず1枚にまとめてから**判断する。
判定基準の詳細は `references/triage-rubric.md`。

| # | 出所(観点) | 指摘 | 提案された修正 | **本当の問題は何か** | 分類 | 対応 |
|---|---|---|---|---|---|---|

- **A 根本** — 受け入れ条件に直結し、原因まで届いている → 直す
- **B スコープ外** — 指摘は正しいが Issue の外 → 別Issue化して返信
- **C 対症療法** — 問題は妥当だが提案の修正が表層的 → **問題は受理、方法は設計し直す**
- **D 観点間矛盾** — 他観点の指摘と両立しない → 手順3へ
- **E 誤検知** — 前提誤り・仕様誤読・意図的な設計 → 根拠を添えて却下

**C と E が1件も無い分類表は、分類が甘い。** 全部 A にした瞬間に沼が始まる。

### 3. コンフリクトを着手前に解く

分類 D と、「A の修正が他観点の合格条件を踏みそうな箇所」を先に洗い出す。
片方ずつ対応するとピンポン・ループになるため、**着手前に**解く。

| # | 観点X の要求 | 観点Y の要求 | 背後の本当の要求(X) | 背後の本当の要求(Y) | 採る解 |

指摘の**表現**は衝突していても、**目的**は衝突していないことが多い。
例:「エラーを握り潰すな」(障害を検知したい) vs「例外を見せるな」(操作を止めたくない)
→ 内部は厳格に記録、UI は回復可能なメッセージ。両方満たす。

解の優先順位: ①両方の背後の要求を満たす第三の設計 → ②層を分けて両立 → ③ゴールに近い方を採り他方に却下理由を返す → ④仕様判断（性能目標・互換性方針・セキュリティ許容度）に依存するなら**人間にエスカレーション**。

### 4. 根本原因に収束させ、統合方針を確定する

A と C について、指摘ではなく原因を書く。

```
- 症状（レビュワーが見たもの）:
- 根本原因:
- この原因を直すと同時に解消される指摘: #, #, #
- 意図的に変更しないもの（B / E）と理由:
- 先回りで手当てする他観点の懸念:
- 検証方法:
```

**複数の指摘が1つの原因に収束したら、それが本命の修正。** 指摘の数だけパッチを当てない。
ここまで書き終えて、はじめてコードを編集する。

### 5. ループを検知したら止める

以下を1つでも観測したら、**実装を停止して人間に判断を仰ぐ**。

1. **3ストライク** — 同一ファイル・同一テーマで3ラウンド連続の指摘
2. **往復** — 自分が入れた修正に対する指摘が2回続く
3. **反転** — 「Xにしろ」で直した箇所に「Xをやめろ」が来た
4. **膨張** — 差分は増え続けるのに受け入れ条件の充足率が上がらない
5. **未着手** — 3ラウンド経ても受け入れ条件のチェックが1つも増えていない

停止時の報告: 経過ラウンド / ゴール再掲 / 充足状況(n件中m件) / 周回しているテーマ / ループ原因の推定 / 提案（設計変更・スコープ縮小・レビュー観点の見直し）/ 判断が必要な点。

**「もう一度レビュワーに投げて様子を見る」は禁止手。** それがループの燃料になる。

## 返信（B / C / D / E は黙って落とさない）

無視すると次ラウンドで同じ指摘が再生成される。1件2〜4行、根拠を1つ添える。

- **C**: 「問題は実在を確認。ただし提案は症状への対処のため、原因である〜を修正した（file:line）。指摘 #N, #M も同時に解消」
- **B**: 「指摘は妥当。ただし受け入れ条件〜の範囲外で本差分が原因でもないため、別Issueとする」
- **D**: 「観点X の〜と両立しないため、双方の要求を満たす〜を採用した」
- **E**: 「file:line を確認したところ〜のため、現状が意図した挙動」

## アンチパターン

- 指摘を1件ずつ順番に潰す（統合設計をしない）
- レビュワーの提案コードをそのまま貼る
- 「レビュワーが通らないから」を理由に設計を歪める
- テストを緩める・アサーションを消す・例外を握り潰して指摘を消す
- 却下を避け、全指摘を機械的に受け入れる
- ループに気づいて「あと1周だけ」と続ける
