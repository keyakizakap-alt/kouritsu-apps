# 分類の判定基準

各指摘を上から順に判定し、最初に該当した分類を採用する。

## E: 誤検知

- レビュワーが参照していない箇所に、既に対処が存在する
- 指摘の前提が実際のコードや実行環境と異なる（読み違え、古い版を見ている）
- 意図的な設計であり、その意図が Issue やコメントに記録されている
- 静的解析・bot の既知の偽陽性

**該当箇所を実際に読んでから判定する。読まずに E と決めない。** 却下理由に file:line を添える。

## D: 観点間矛盾

- この指摘に従うと、別観点が不合格にする条件を踏むと分かっている
- 過去ラウンドで、この修正の逆方向の指摘を受けたことがある
- 指摘同士がトレードオフの両端にある（下表）

単独で着手せず、SKILL.md の手順3へ送る。

## B: 正当だがスコープ外

- 技術的には正しいが、受け入れ条件のどれにも紐づかない
- 今回の差分が原因ではない既存の問題
- 「ついでにこれも直すべき」型の提案

**注意**: 自分の差分が引き金で顕在化した既存問題は B ではなく A/C。必ず確認する。

## C: 対症療法

指摘された**問題**は実在するが、提案された**修正方法**が次のいずれか。

- 例外を握り潰す / 条件分岐を足して個別ケースだけ回避する
- 呼び出し側だけ直し、原因のある呼ばれる側を放置する
- テストを通すためのハードコード、閾値の緩和、アサーションの削除
- 同じ問題が他箇所にもあるのに、指摘された1箇所だけ直す
- 型・null・境界値の問題をキャストや非nullアサーションで黙らせる

問題は受理し、修正方法は自分で設計し直す。

## A: 根本

上のいずれにも当たらず、受け入れ条件に直結し、提案された修正が原因そのものに届いている。

# 分類後の健全性チェック

- 全件が A になっていないか → 分類が甘い。C と E を疑う
- 全件が E になっていないか → 防衛的すぎる。指摘を読み直す
- 同一の根本原因に紐づく A/C が複数ないか → 1つの統合パッチにまとめる
- 前回 A として直した箇所に再指摘が来ていないか → **前回の修正が実は C だった証拠。根本に遡る**

# よく出るコンフリクトの型

| 型 | 典型的な衝突 | 統合解の方向 |
|---|---|---|
| 堅牢性 vs UX | 例外を投げる / 握って表示 | 記録は厳格に、表示は穏当に |
| 抽象化 vs 単純さ | 共通化しろ / 過剰設計だ | 3回目の重複まで共通化しない |
| 性能 vs 可読性 | 最適化しろ / 読めない | 計測で必要性を示せた箇所のみ最適化し、理由をコメントに残す |
| 厳格な型 vs 後方互換 | 型を絞れ / 既存が壊れる | 新APIを追加し、旧APIは非推奨として残す |
| 網羅テスト vs 差分最小 | ケースを足せ / スコープ外だ | 受け入れ条件に紐づくケースのみ今回、残りは別Issue |
| セキュリティ vs 利便性 | 検証を足せ / 手順が増える | 安全側をデフォルトにし、緩和は明示的なオプトインに |
