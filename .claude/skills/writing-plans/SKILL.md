# writing-plans — 実装計画を書く

**このリポジトリの文脈を一切知らない実装者**が読んで、そのまま実行できる計画を書く。
腕は確かだが、このプロジェクトのツールセットも問題領域も知らず、テスト設計も得意ではない、
という前提を置く。必要な情報は全部書く。

**開始時に宣言する:**「writing-plans スキルで実装計画を作ります」

**保存先:** `docs/plans/YYYY-MM-DD-<機能名>.md`

**前提:** 承認済みの設計／仕様があること。無いなら `brainstorming` に戻る。

原則: **DRY / YAGNI / TDD / こまめなコミット。**

## スコープ確認

仕様が独立した複数のサブシステムに跨っているなら、**計画を分ける**ことを提案する。
1つの計画は、それ単体で動作しテスト可能なソフトウェアを生むこと。

## ファイル構成を先に決める

タスクを定義する前に、どのファイルを作り／変更し、それぞれ何に責任を持つかを書き出す。
ここで分割の判断が固まる。

- 境界が明確で、インターフェースが定義された単位に設計する。1ファイル1責任
- **一度に文脈へ載せられる大きさのコードのほうが、正確に読み書きできる。**大きすぎるファイルより、焦点の絞られた小さいファイルを選ぶ
- 一緒に変わるものは一緒に置く。技術レイヤーではなく責務で分ける
- 既存コードベースでは既存のパターンに従う。大きいファイルを使う方針なら勝手に再編しない。
  ただし手を入れるファイルが手に負えなくなっているなら、分割を計画に含めてよい

## タスクの粒度

**タスク** = 自前のテストサイクルを持ち、レビュー対象として意味がある最小単位。

- セットアップ・設定・足場・ドキュメントは、それを必要とする成果物のタスクに畳み込む
- 「片方を承認し、もう片方を却下できる」境界でのみ分割する
- 各タスクは、単独でテスト可能な成果物で終わる

**ステップ** = 1アクション（2〜5分）。

- 「失敗するテストを書く」
- 「実行して失敗を確認する」
- 「テストを通す最小限の実装を書く」
- 「実行して通ることを確認する」
- 「コミットする」

## 計画書のヘッダ

**すべての計画はこのヘッダで始める:**

```markdown
# <機能名> 実装計画

> **実装者へ:** 本計画は `executing-plans` スキルに従ってタスク単位で実装すること。
> ステップはチェックボックス（`- [ ]`）で進捗を管理する。

**ゴール:** （何を作るか1文）
**構成:** （方針を2〜3文）
**技術スタック:** （主要な技術・ライブラリとバージョン）
**設計文書:** `docs/specs/YYYY-MM-DD-<topic>-design.md`
**検証コマンド:** （このリポジトリで通すコマンド。CLAUDE.md を参照）

## 全体制約

（設計から持ってくるプロジェクト全体の要件。バージョン下限、依存の制限、
命名・文言のルール、対応環境。1行ずつ、値は設計から逐語でコピーする。
各タスクの要件にはこの節が暗黙に含まれる。）

---
```

## タスクの書式

````markdown
### タスク N: <コンポーネント名>

**ファイル:**
- 作成: `exact/path/to/file.ts`
- 変更: `exact/path/to/existing.ts:123-145`
- テスト: `tests/exact/path/to/file.test.ts`

**インターフェース:**
- 使うもの: （先行タスクから受け取るもの。正確なシグネチャ）
- 提供するもの: （後続タスクが依存するもの。正確な関数名・引数型・戻り値型。
  実装者は自分のタスクしか見ないため、隣のタスクの名前と型はここでしか分からない）

- [ ] **ステップ1: 失敗するテストを書く**

```ts
test('空のメールアドレスを拒否する', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('メールアドレスを入力してください');
});
```

- [ ] **ステップ2: 実行して失敗を確認する**

実行: `npm test -- tests/form.test.ts`
期待: FAIL（`result.error` が undefined）

- [ ] **ステップ3: 最小限の実装を書く**

```ts
function submitForm(data: FormData) {
  if (!data.email?.trim()) return { error: 'メールアドレスを入力してください' };
  // ...
}
```

- [ ] **ステップ4: 実行して通ることを確認する**

実行: `npm test -- tests/form.test.ts`
期待: PASS

- [ ] **ステップ5: コミット**

```bash
git add tests/form.test.ts app/form.ts
git commit -m "feat: 空メールアドレスのバリデーションを追加"
```
````

## プレースホルダ禁止

各ステップには、実装者が必要とする実際の中身を書く。以下は**計画の不備**であり、書いてはならない。

- 「TBD」「TODO」「後で実装」「詳細は後ほど」
- 「適切にエラーハンドリングする」「バリデーションを追加する」「エッジケースを処理する」
- 「上記のテストを書く」（実際のテストコードが無い）
- 「タスク N と同様」（コードを繰り返す。実装者は順番に読むとは限らない）
- 何をするかだけ書いて、どうやるかを示さない（コードのステップにはコードブロックが必須）
- どのタスクでも定義していない型・関数・メソッドへの参照

## セルフレビュー（計画を書き終えたあと）

新しい目で仕様と計画を突き合わせる。自分で回すチェックであり、サブエージェントには投げない。

1. **仕様の網羅**: 仕様の各節・各要件について、実装するタスクを指させるか。抜けを列挙する
2. **プレースホルダ走査**: 上記の禁止パターンを検索して潰す
3. **型の整合**: 後半のタスクで使っている型・シグネチャ・プロパティ名は、前半の定義と一致しているか
   （タスク3で `clearLayers()`、タスク7で `clearFullLayers()` はバグ）

見つけたらその場で直す。仕様の要件に対応するタスクが無ければ、タスクを追加する。

## 実装への引き渡し

保存後、こう伝える。

> 計画を `docs/plans/<ファイル名>.md` に保存しました。
> `executing-plans` スキルでタスク単位に実装します。着手してよいですか。
